---
title: Live Props
---

Sometimes you may wish for a prop to stay in sync with your server without the user doing anything. Live props subscribe to your broadcast events and refresh the props those events affect, making them ideal for order statuses, unread counts, dashboard metrics, or anything a background job updates.

A live prop is refreshed with a [partial reload](/v3/data-props/partial-reloads), so the value the client receives is whatever your controller resolves at that moment. The broadcast event is only a signal that something changed. An event may also [carry the new values](#broadcasting-values) itself, in which case no request is made at all.

## Creating Live Props

To create a live prop, use the `Inertia::live()` method and pass the event that should refresh it.

```php
use App\Events\OrderUpdated;

return Inertia::render('Orders/Show', [
    'order' => Inertia::live(fn () => $order->fresh(), on: new OrderUpdated($order)),
]);
```

The channel is read from the event's `broadcastOn()` method, so an event that already broadcasts on `new PrivateChannel('orders.'.$order->id)` needs no further configuration. Whenever that event broadcasts, the client reloads the `order` prop.

Live props may be composed with [deferred props](/v3/data-props/deferred-props), [once props](/v3/data-props/once-props), [optional props](/v3/data-props/partial-reloads#lazy-data-evaluation), and always props. An optional live prop is only refreshed once the page has loaded it, so an event never loads a prop the page did not ask for. [Merge props](/v3/data-props/merging-props) may not be live.

```php
return Inertia::render('Orders/Show', [
    'metrics' => Inertia::defer(fn () => $order->metrics())->live(on: new OrderUpdated($order)),
]);
```

## Client Setup

Live props receive their events through a transport, which you pass to the `live` option of `createInertiaApp()`. Inertia ships transports for [Laravel Echo](https://laravel.com/docs/broadcasting#client-side-installation), `pusher-js`, and Action Cable.

### Echo

Configure Echo as you normally would, then pass the transport.

<CodeGroup>

```js Vue icon="vuejs"
import { createInertiaApp } from "@inertiajs/vue3";
import { echo } from "@inertiajs/vue3/echo";
import { configureEcho } from "@laravel/echo-vue";

configureEcho({ broadcaster: "reverb" });

createInertiaApp({
  live: echo(),
  // ...
});
```

```js React icon="react"
import { createInertiaApp } from "@inertiajs/react";
import { echo } from "@inertiajs/react/echo";
import { configureEcho } from "@laravel/echo-react";

configureEcho({ broadcaster: "reverb" });

createInertiaApp({
  live: echo(),
  // ...
});
```

```js Svelte icon="s"
import { createInertiaApp } from "@inertiajs/svelte";
import { echo } from "@inertiajs/svelte/echo";
import { configureEcho } from "@laravel/echo-svelte";

configureEcho({ broadcaster: "reverb" });

createInertiaApp({
  live: echo(),
  // ...
});
```

</CodeGroup>

The transport uses the Echo instance configured by `configureEcho()`. You may pass a `resolve` callback to `echo()` to provide an Echo instance yourself.

### Pusher

You may also deliver updates using `pusher-js` directly, which works with any server speaking the Pusher protocol, such as [Reverb](https://reverb.laravel.com). Configure the client yourself, including channel authorization, and pass it to the `pusher()` transport.

```js
import { pusher } from "@inertiajs/core/pusher";
import Pusher from "pusher-js";

const client = new Pusher("pusher-app-key", {
  // ...
});

createInertiaApp({
  live: pusher({ client }),
  // ...
});
```

### Action Cable

Rails applications may deliver updates over [Action Cable](https://guides.rubyonrails.org/action_cable_overview.html) instead. Pass a function that creates the consumer, so Inertia opens a single connection the first time a page subscribes, and never during server-side rendering.

```js
import { actionCable } from "@inertiajs/core/actionCable";
import { createConsumer } from "@rails/actioncable";

createInertiaApp({
  live: actionCable({ consumer: () => createConsumer() }),
  // ...
});
```

Each live channel is subscribed to `InertiaChannel` with the channel's `stream` and `type` as params. You may pass the `channel` option to use a different channel class, or an `identifier` function to build the params yourself. Since Action Cable messages carry no event name, the server sends it along in an `__inertia` envelope, which Inertia reads to decide which props an event feeds.

```json
{ "__inertia": { "event": "order.updated" } }
```

No further client-side setup is required. Inertia reads the subscriptions from each page response, subscribing and unsubscribing as the user navigates.

## Listening for Multiple Events

You may pass an array of events to refresh a prop from more than one event. Each event keeps its own channel, so events that broadcast in different places may safely feed the same prop.

```php
return Inertia::render('Orders/Show', [
    'order' => Inertia::live(fn () => $order->fresh(), on: [
        new OrderUpdated($order),
        new OrderShipped($order),
    ]),
]);
```

Several props may also listen for the same event. Inertia subscribes once per channel and event pair, and props refreshed by the same event are reloaded together in a single request.

## Channels

Live props use the channels your events already broadcast on, so the [Laravel broadcasting documentation](https://laravel.com/docs/broadcasting#defining-broadcast-events) applies as is. A prop subscribes to every channel its event broadcasts on, so an event that broadcasts on both `orders.1` and a shared `orders` channel refreshes the prop whenever any order changes.

You may pass the `channel` argument to subscribe to a specific channel instead.

```php
return Inertia::render('Dashboard', [
    'metrics' => Inertia::live(fn () => Metrics::today(), on: OrderUpdated::class, channel: new PrivateChannel('orders')),
]);
```

Passing a class name rather than an instance works whenever the event's channels are fixed, since Inertia builds the event without its payload to read them.

```php
class OrderUpdated
{
    public function broadcastOn(): PrivateChannel
    {
        return new PrivateChannel('orders');
    }
}

Inertia::live(fn () => $order->fresh(), on: OrderUpdated::class);
```

An event that builds its channel from the payload, such as `new PrivateChannel('orders.'.$this->order->id)`, throws an exception since there is no payload to read from. Pass an instance, or name the channel yourself.

```php
Inertia::live(fn () => $order->fresh(), on: new OrderUpdated($order));
Inertia::live(fn () => $order->fresh(), on: OrderUpdated::class, channel: new PrivateChannel('orders.'.$order->id));
```

The same applies to an event whose `broadcastAs()` method builds the broadcast name from its payload.

Channels behave as they do anywhere else in Laravel. A bare string is a public channel, and each channel class defines its own type.

```php
use Illuminate\Broadcasting\Channel;
use Illuminate\Broadcasting\EncryptedPrivateChannel;
use Illuminate\Broadcasting\PresenceChannel;
use Illuminate\Broadcasting\PrivateChannel;

$channel = 'stats';                                   // public
$channel = new Channel('stats');                      // public
$channel = new PrivateChannel('orders.1');            // private
$channel = new PresenceChannel('room.1');             // presence
$channel = new EncryptedPrivateChannel('orders.1');   // encrypted private

Inertia::live($value, on: $event, channel: $channel);
```

The channels an event returns from `broadcastOn()` are read the same way, so wrap the name in a channel class there too unless the event is meant to be public.

```php
public function broadcastOn(): array
{
    return ['stats'];                           // public
    return [new PrivateChannel('orders.1')];    // private
}
```

Private, presence, and encrypted private channels are authorized through your `channels.php` routes like any other channel subscription. See [authorizing channels](https://laravel.com/docs/broadcasting#authorizing-channels) in the Laravel documentation.

## Throttling

By default, each live prop refreshes at most once per second. You may change this default by passing a `throttle` value in milliseconds to `echo()`, `pusher()`, or `actionCable()`.

<CodeGroup>

```js Vue icon="vuejs"
import { createInertiaApp } from "@inertiajs/vue3";
import { echo } from "@inertiajs/vue3/echo";

createInertiaApp({
  live: echo({ throttle: 2000 }),
  // ...
});
```

```js React icon="react"
import { createInertiaApp } from "@inertiajs/react";
import { echo } from "@inertiajs/react/echo";

createInertiaApp({
  live: echo({ throttle: 2000 }),
  // ...
});
```

```js Svelte icon="s"
import { createInertiaApp } from "@inertiajs/svelte";
import { echo } from "@inertiajs/svelte/echo";

createInertiaApp({
  live: echo({ throttle: 2000 }),
  // ...
});
```

</CodeGroup>

A prop may also set its own throttle, which takes precedence over the default.

```php
return Inertia::render('Dashboard', [
    'metrics' => Inertia::live(fn () => Metrics::today(), on: new MetricsUpdated, throttle: 5000),
]);
```

Each prop keeps its own throttle window, so a busy prop never delays the rest of the page. Events that arrive during the window are not dropped. Instead, they are collected into a single request once the window expires. Throttling only limits requests, so [values carried by a broadcast](#broadcasting-values) are applied immediately.

Manual reloads are never throttled, so you may always fetch a prop yourself using `router.reload({ only: ['order'] })`.

Refreshes pause while the browser tab is hidden and resume when the user returns. You may pass `pauseWhenHidden: false` to the transport to keep refreshing hidden tabs. Values carried by a broadcast are applied either way.

## Collecting Bursts

A single server action often broadcasts several events, which reach the browser a few milliseconds apart. Inertia waits briefly before sending the first request of a burst, then refreshes every prop the burst touched in a single request.

Events that arrive after that request has been sent refresh their props once the prop's [throttle](#throttling) window ends, so every prop the burst touched ends up refreshed.

## Broadcasting Values

By default, an event is only a signal, and every listening page asks the server for the new value. This keeps each value specific to the user, since your controller resolves it for them. However, a dashboard open in a thousand tabs turns one event into a thousand requests.

Instead, an event may carry the values itself. You may return them from the event's `broadcastWith()` method using `Inertia::broadcastProps()`, alongside any other data the event sends.

```php
class OrderUpdated implements ShouldBroadcast
{
    public function __construct(public Order $order) {}

    public function broadcastOn(): PrivateChannel
    {
        return new PrivateChannel("orders.{$this->order->id}");
    }

    public function broadcastWith(): array
    {
        return [
            'order_id' => $this->order->id,
            ...Inertia::broadcastProps([
                'order' => OrderResource::make($this->order),
            ]),
        ];
    }
}
```

Inertia writes those values straight into the page, so no request is made at all. The keys are prop names, and nested props use their dot path, the same way `only` does on a partial reload.

Values are only applied to props that listen for the event, so an event may safely carry values for props that some pages don't have. Props the event doesn't carry a value for are refreshed with a request as usual, so an event may carry some values and leave the rest to the server.

Values are resolved exactly as page props are, keeping their shape identical to what a refresh would have produced. Resources, `Arrayable` objects, and closures all work. Pass the value itself rather than a prop type such as `Inertia::optional()`, since a prop that is omitted during resolution cannot be broadcast.

A carried value is discarded while a refresh for that prop is already in flight, and the prop is refreshed instead, since that request may have read newer data than the event carries.

Events are applied in the order they arrive. Nothing reorders them, so an event that overtakes another leaves the prop showing the older value until the next event for that prop arrives.

### Every Subscriber Receives the Same Values

Channel authorization decides who may join a channel. It does not decide what each member is allowed to see, and a broadcast delivers identical bytes to everyone listening. A refreshed prop is resolved per request, with that user's session, policies, locale, and visibility rules. A carried value cannot be.

Only carry values that are the same for every subscriber of the channel. A private channel alone is not enough, since a channel with several members, such as a team or presence channel, delivers the same payload to all of them. Anything that varies per user belongs on the refresh path, where your controller resolves it.

Returning a model rather than a resource serializes it using `toArray()`, which respects `$hidden` but knows nothing about the fields your resource omits. A resource that reads from the request also behaves differently inside a queued event, where there is no real request to read.

Authorization is only checked when the subscription is established, not per event. Props whose data must stop reaching a user the moment their access is revoked should stay on the refresh path.

## Tracking Refreshes

The `useProp` hook returns a prop's value along with whether it is currently being refreshed, making it ideal for rendering a subtle loading indicator without blocking the UI.

<CodeGroup>

```vue Vue icon="vuejs"
<script setup>
import { useProp } from "@inertiajs/vue3";

const { value: order, loading } = useProp("order");
</script>

<template>
  <div :class="{ 'opacity-50': loading }">
    {{ order.status }}
  </div>
</template>
```

```jsx React icon="react"
import { useProp } from "@inertiajs/react";

export default () => {
  const order = useProp("order");

  return <div className={order.loading ? "opacity-50" : ""}>{order.value.status}</div>;
};
```

```svelte Svelte icon="s"
<script>
  import { useProp } from "@inertiajs/svelte";

  const order = useProp("order");
</script>

<div class={order.loading ? "opacity-50" : ""}>
  {order.value.status}
</div>
```

</CodeGroup>

A `loaded` value is also returned, which reports whether the prop has arrived yet. This is useful for a live prop that is also [deferred](/v3/data-props/deferred-props).

## Live Events

Inertia fires a cancelable [`live` event](/v3/advanced/events#live) before updating a live prop. Returning `false` from the listener skips the update, including any values the event carries, letting you show a "New data available" button instead of updating the page under the user. You may later apply the update using `router.reload({ only: event.detail.props })`.

```js
router.on("live", (event) => {
  console.log(event.detail.props); // the props about to be refreshed
  console.log(event.detail.channel); // { name, type }
  console.log(event.detail.event); // the broadcast event name
  console.log(event.detail.payload); // the broadcast payload

  return false;
});
```

## Skipping the Current Connection

Inertia sends the broadcaster's socket ID as the `X-Socket-Id` header with every request it makes to your application, so `toOthers()` works as expected and the user who caused a change is not refreshed by their own broadcast. Requests to other origins never receive it.

```php
broadcast(new OrderUpdated($order))->toOthers();
```

You may resolve the socket ID yourself using `socketId.resolveUsing()`. Your resolver takes precedence over the transport's, regardless of whether you register it before or after calling `createInertiaApp()`. Passing `null` stops sending the header entirely.

<CodeGroup>

```js Vue icon="vuejs"
import { socketId } from "@inertiajs/vue3";

socketId.resolveUsing(() => mySocket.id);
socketId.resolveUsing(null);
```

```js React icon="react"
import { socketId } from "@inertiajs/react";

socketId.resolveUsing(() => mySocket.id);
socketId.resolveUsing(null);
```

```js Svelte icon="s"
import { socketId } from "@inertiajs/svelte";

socketId.resolveUsing(() => mySocket.id);
socketId.resolveUsing(null);
```

</CodeGroup>

Action Cable issues no socket ID and cannot exclude a connection from a broadcast, so the Action Cable transport generates an ID per browser tab and sends it instead. The server includes the ID of the connection that caused the event as `__inertia.socketId`, and that tab ignores the event. A custom transport without a `socketId` sends no header at all.

## Custom Transports

You may pass any object implementing the `LiveTransport` interface to the `live` option, allowing you to deliver updates over your own WebSocket client, a server-sent events stream, or a `BroadcastChannel`.

```ts
import type { LiveTransport } from "@inertiajs/core";

const transport: LiveTransport = {
  subscribe(channel, event, handler) {
    // Called once per channel and event pair. Return a function that unsubscribes.
    return () => {};
  },

  // Optional. Lets Inertia send the socket ID so `toOthers()` works.
  socketId: () => connection.id,

  // Optional. Inertia refreshes every live prop after a dropped connection
  // returns, since events that fired while it was down never arrived.
  onStatusChange(callback) {
    return () => {};
  },
};
```

The `subscribe()` method runs during a page swap, so avoid throwing from it for anything recoverable, as an error there aborts the page swap.

The `onStatusChange()` callback receives a boolean indicating whether the connection is up. Inertia only acts when a dropped connection is restored, so reporting the same status repeatedly, or once per channel, is safe.

```ts
onStatusChange(callback) {
  const handler = (state: string) => callback(state === "connected");

  connection.on("state_change", handler);

  return () => connection.off("state_change", handler);
}
```

Channel names arrive unprefixed alongside their type, such as `{ name: "orders.1", type: "private" }`, so the transport is responsible for applying the prefix your broadcaster expects. Inertia subscribes per channel and event pair, so a transport for a broadcaster that subscribes per channel should join a channel on its first listener and leave it after its last.

### Channel Transports

Some broadcasters cannot route messages by event name. Transports for these broadcasters may implement `subscribeToChannel()` instead, which is called once per channel. Inertia reads the event name from the `__inertia.event` key of each message and routes it to the props that event feeds.

```ts
import type { LiveChannelTransport } from "@inertiajs/core";

const transport: LiveChannelTransport = {
  subscribeToChannel(channel, handler) {
    const stream = socket.subscribe(channel.name, handler);

    return () => stream.close();
  },

  // Optional. Reads the event name from somewhere other than `__inertia.event`.
  eventName: (payload) => payload.type,
};
```

A channel may also carry `params`, which the server sets and Inertia passes to the transport untouched. Channels are told apart by their type and name, so params should stay the same for a given channel.
